# Project layout

The Screeps Arena client loads `src/main.mjs` from the selected `src/` code directory and calls its exported `loop()` once per tick. This entry point delegates to `runTick()` in `src/loop.js`.

The current tick flow is:

1. `src/arena/observe.js` reads the tick number with `getTicks()`, calls `getObjectsByPrototype` for ScoreFlags and Creeps, retains all observed creeps for logging, then separates owned creeps, living enemies, and damaged living allies.
2. `src/strategy/objectives.js` selects the first ScoreFlag in the returned order. The disabled-by-default `src/config.js` switches independently enable `src/strategy/flag-allocation.js` for one bounded scout attempt and `src/tactics/healer-escort.js` for one pre-injury healer/melee pair. Scout allocation changes only that scout's fallback objective, not the globally selected/logged first flag.
3. On the first successful tick, `src/arena/observe.js` samples the 100×100 terrain and all non-creep game objects; `src/debug/game-state.js` emits one `map-state` JSON line. It then emits one `game-state` line on every tick with the tick, selected flag ID, creep ownership/positions/health/fatigue/functioning body-part counts, and flag ownership/effects/scoring rates. With the optional scout experiment enabled, the planner additionally emits structured `flag-allocation` decisions, including the exact `searchPath` result fields used for evaluated routes; only consecutive identical route-free rejections are collapsed. The optional escort emits assignment/release decisions before actions and an assigned-healer movement result when executed. The map is an initial snapshot and does not retain later ownership changes.
4. `src/tactics/movement.js` chooses one movement objective per owned creep. An armed creep approaches the nearest living enemy within five tiles until within its weapon range; a mixed-weapon creep seeks melee range. If no enemy is within five tiles, a target selected on the preceding tick can be retained for one tick at range six. A second outside tick, range seven, lost target, or lost weapon releases it. An in-range combatant holds position. A pure healer with a functioning HEAL part approaches the nearest living damaged ally outside its heal range (four or five tiles away), holds when no such ally exists but one is within three tiles, and otherwise falls back to the first flag. Mixed-role healers keep combat movement. With the optional scout experiment enabled, only the assigned MOVE-only scout receives an alternate flag fallback; combat and healer decisions still take precedence. With the optional escort enabled, one assigned pure healer instead holds within range two of its engaging melee partner or attempts `moveTo(partner)` at range three to five while everyone remains healthy. Any injury releases it before movement selection that tick, restoring normal injured-ally support. `src/arena/execute.js` issues at most one `moveTo` command per creep. `src/loop.js` retains per-creep combat targets and the one-attempt experimental states, resetting them when the tick counter restarts.
5. `src/tactics/healing.js` and `src/tactics/combat.js` select eligible actions, which `src/arena/execute.js` issues for each owned creep after movement.

The game-state log is an observation before this tick's actions, not a report of their results. The allocation diagnostic describes a planner decision and fallback objective, not an issued `moveTo`, successful movement, capture, or benefit. Escort assignment/release diagnostics describe planner transitions. Escort execution diagnostics distinguish a hold, fatigue pause, and actual `moveTo` attempt, including its returned API code; even `OK` does not prove displacement. Health changes across ticks do not by themselves prove action causality. Logging does not change action order.

`src/tactics/body.js` checks for functioning body parts (`hits > 0`). `src/tactics/targets.js` chooses the nearest eligible target, breaking equal-range ties by ID and then observation order. Movement considers enemies within five tiles; this keeps combat positioning local while preserving the flag objective when enemies are farther away. A damaged healer heals itself first; otherwise it heals the nearest damaged ally within range 1 or uses `rangedHeal` within range 3. Available healing takes priority over conflicting attacks: `heal` can accompany `rangedAttack`, but not `attack`; `rangedHeal` excludes both attacks. Without healing, adjacent creeps with both attack parts can use both attacks. Tactical actions are chosen after movement commands, using current observed positions rather than predicted positions.

The bot maintains per-creep combat-target IDs and a one-tick boundary-grace counter. Normal injured-ally support is recomputed from current positions each tick; the disabled escort experiment can additionally retain one healer/melee pair for at most 12 ticks. It does not form squads, retreat, or draw overlays. Further modules belong under the requested `src/` folders only when the corresponding behavior is introduced.

Movement ranks targets by linear distance, not terrain route cost. `moveTo` performs navigation and can fail to make progress because of fatigue, missing MOVE parts, obstacles, or congestion. Mixed-weapon closing, competing injured allies, healer exposure, and approach/fallback switching after the one-tick grace are tradeoffs of this policy. The [combat-positioning validation](combat-positioning-validation.md) records map-linked evidence, local checks, and live-runtime limitations.

The opt-in allocation uses `searchPath` with a bounded operation count to require a complete terrain route and estimate steps for the scout and nearby competitors. A competitor must arrive strictly later than the scout estimate plus five steps; equality rejects the target. Terrain routes omit moving obstacles, fatigue, damage, and future enemy decisions; geometric range is used only as a lower bound when it already proves an enemy is farther away. A capture is not undone when the scout returns: the flag keeps scoring and imposing its army-wide penalty while owned. See the [experiment policy](combat-positioning-validation.md#one-scout-flag-allocation-experiment--2026-09-28).

Local Node.js tests import the pure selection and execution modules. Arena-specific imports stay at the observation and tick-orchestration boundaries (`observe.js` and the optional route search in `loop.js`); `package.json` and Node.js test APIs are for local tooling only. Relative imports remain inside `src/`, because Arena uses the directory containing `main.mjs` as the code root.

## Local replay imports

The local `tools/build-id.js` command generates and verifies `src/debug/build-id.js`. It hashes sorted project-relative paths and exact bytes of runtime `.js`/`.mjs` files under `src/` with NUL separators, excluding the generated file itself and `src/typings/`. The runtime logger emits this ID with pre-action map and game-state entries. The importer records tagged response IDs and a replay association independently of map identity; conflicting tags are rejected, while legacy untagged response provenance stays unknown. See the README for the pre-launch commands and precise hash rule.

`tools/replay-logs.js` is a separate Node.js CLI outside the Arena code directory. It reads cached replay-log responses at startup and polls for changes while the user controls replay playback. Request metadata establishes replay identity; supported version-5 cache framing and gzip payloads yield the original console JSON strings. Arena may join multiple console calls from one tick with a newline; the importer separates and validates each before preserving game-state strings in JSONL. It validates build-tagged allocation and escort diagnostics and retains their original lines as typed manifest `otherEntries`, separate from warnings/errors and from the game-state JSONL. Legacy responses without diagnostics remain valid. Distinct response contents receive separate captures under `replay_logs/`, with hash suffixes when the replay's canonical filename is occupied. A response's observed tick range does not establish full replay coverage.

The importer extracts the creep-free `map-state` entry, saves its map content with a top-level `checksum` as JSON under `replay_logs/pain_and_gain_map_<UTC-date>.json`, and registers that checksum and map ID in manifest version 2. SHA-256 covers canonical payload JSON plus a newline, excluding only the top-level checksum field; recursive key sorting and array order remain unchanged. A map is validated only when its saved payload passes schema checks and its embedded, registered, and recalculated checksums agree. Identical content reuses a validated registration even across replays. Each replay has its own explicit active map association; there is no global active map. A game-state response arriving before its replay's map is deferred, not written as JSONL, and retried when the map arrives. Every imported record names its map ID, checksum, and file. The JSONL preserves only original game-state console strings. No map is inferred for older unlinked captures.

The explicit `upgrade-map-checksums` command locks the manifest, verifies legacy saved payloads against existing registrations, and atomically embeds missing checksums. It preserves registrations and all manifest bytes, reports failures per map without replacing mismatched values, and is safe to retry. Normal validation requires the embedded field. An orphaned map publication can be reused only after matching the verified incoming payload; a conflicting embedded checksum is rejected. Neither checksum embedding nor validation changes runtime console records.

`replay_logs/manifest.json` has `maps`, `replays`, and `records` collections. A record moves from transient import status `pending` to `claim` while analysis is pending; task ownership claims are stored separately in `reviews`. Existing `waiting` records migrate to `claim` under the manifest lock without losing checkpoints, map associations, or fingerprints. Records retain source fingerprint, output ownership and hash, coverage, other console entries, and per-task review checkpoints. Pending imports are recorded before atomic file publication so a retry can finish an interrupted import. Manifest updates and cleanup share a process lock. A local JSONL file can be explicitly registered only when its replay already has a validated active map association and its game-state flags match that map; JSONL alone cannot prove replay identity. Claims retain captures until every claiming task explicitly records examination and completion after saving findings outside the manifest. Only then does the record become `done`; cleanup checks the managed path and content hash before deleting the JSONL and its record. Map files and registrations remain. A replay association retains retired fingerprints to prevent unchanged data from reimporting, but not the deleted log's review history. Unregistered reference files are never adopted automatically. Empty version-1 manifests migrate automatically; nonempty version-1 manifests require deliberate migration before using this importer. CLI commands and format limitations are documented in `README.md`.
