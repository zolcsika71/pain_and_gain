# Project layout

The Screeps Arena client loads `src/main.mjs` from the selected `src/` code directory and calls its exported `loop()` once per tick. This entry point delegates to `runTick()` in `src/loop.js`.

The current tick flow is:

1. `src/arena/observe.js` reads the tick number with `getTicks()`, calls `getObjectsByPrototype` for ScoreFlags and Creeps, retains all observed creeps for logging, then separates owned creeps, living enemies, and damaged living allies.
2. `src/loop.js` updates match-local `src/squads/membership.js` bookkeeping from the owned pre-action creeps, resetting it when the tick counter restarts. `src/debug/replay-evidence.js` observes the resulting state and emits a full version-1 baseline per loaded epoch followed by change-only membership records. Diagnostics do not mutate membership or drive gameplay. The disabled `squadPairExperiment` optionally passes membership to the one-pair movement planner. `src/strategy/objectives.js` selects the first ScoreFlag in the returned order. The `src/config.js` switches independently control `src/strategy/flag-allocation.js` for one bounded scout attempt and `src/tactics/healer-escort.js` for one pre-injury healer/melee pair. The prepared activation enables healer escort while scout allocation remains disabled. Scout allocation changes only that scout's fallback objective, not the globally selected/logged first flag.
3. On the first successful tick, `src/arena/observe.js` samples the 100×100 terrain and all non-creep game objects; `src/debug/game-state.js` emits one `map-state` JSON line. It then emits one `game-state` line on every tick with the tick, selected flag ID, creep ownership/positions/health/fatigue/functioning body-part counts, and flag ownership/effects/scoring rates. With the optional scout experiment enabled, the planner additionally emits structured `flag-allocation` decisions, including the exact `searchPath` result fields used for evaluated routes; only consecutive identical route-free rejections are collapsed. The optional escort emits assignment/release decisions before actions and an assigned-healer movement result when executed. Existing movement and tactical paths emit versioned decisions before commands and attempts immediately after the original command returns. After actions, `src/loop.js` reads elapsed CPU with `getCpuTime()` and the applicable first/ordinary-tick Arena limit. The replay-evidence logger emits that sample, then closes the tick with exact sequence/count metadata. The map is an initial snapshot and does not retain later ownership changes.
4. `src/tactics/movement.js` chooses one movement objective per owned creep. An armed creep approaches the nearest living enemy within five tiles until within its weapon range; a mixed-weapon creep seeks melee range. If no enemy is within five tiles, a target selected on the preceding tick can be retained for one tick at range six. A second outside tick, range seven, lost target, or lost weapon releases it. An in-range combatant holds position. A pure healer with a functioning HEAL part approaches the nearest living damaged ally outside its heal range (four or five tiles away), holds when no such ally exists but one is within three tiles, and otherwise falls back to the first flag. Mixed-role healers keep combat movement. With the optional scout experiment enabled, only the assigned MOVE-only scout receives an alternate flag fallback; combat and healer decisions still take precedence. With the optional escort enabled, one assigned pure healer instead holds within range two of its engaging melee partner or attempts `moveTo(partner)` at range three to five. Any injury still blocks acquisition. An existing pair releases before movement selection when either partner is injured or another injured friendly is within five tiles of the assigned healer; a more distant unrelated injury alone does not release it. The disabled squad-pair experiment coordinates two members only while both select first-flag fallback, yielding to escort and other movement priorities. `src/arena/execute.js` issues at most one `moveTo` command per creep. `src/loop.js` retains per-creep combat targets and the one-attempt experimental states, resetting them when the tick counter restarts.
5. `src/tactics/healing.js` and `src/tactics/combat.js` select eligible actions, which `src/arena/execute.js` issues for each owned creep after movement.

The game-state log is an observation before this tick's actions, not a report of their results. Membership evidence describes the bookkeeping state after its production update; it is not formation or squad-behavior evidence. M2 membership-only, M3 action, and current version-2 CPU-covering closures remain distinguishable. M3 decisions include explicit holds and no-actions; attempts record the original method, argument coordinates, and direct numeric return or `null` when no numeric value was returned. `OK` proves scheduling, not displacement, damage, or healing, and a missing attempt remains unknown. A CPU sample is elapsed wall time through its call; its own emission and the closure follow it, so derived headroom is not guaranteed final headroom or differential logging overhead. The allocation diagnostic describes a planner decision and fallback objective, not an issued `moveTo`, successful movement, capture, or benefit. Escort assignment/release diagnostics describe planner transitions. Health changes across ticks do not by themselves prove action causality. Logging does not change action order.

`src/tactics/body.js` checks for functioning body parts (`hits > 0`). `src/tactics/targets.js` chooses the nearest eligible target, breaking equal-range ties by ID and then observation order. Movement considers enemies within five tiles; this keeps combat positioning local while preserving the flag objective when enemies are farther away. A damaged healer heals itself first; otherwise it heals the nearest damaged ally within range 1 or uses `rangedHeal` within range 3. Available healing takes priority over conflicting attacks: `heal` can accompany `rangedAttack`, but not `attack`; `rangedHeal` excludes both attacks. Without healing, adjacent creeps with both attack parts can use both attacks. Tactical actions are chosen after movement commands, using current observed positions rather than predicted positions.

The bot maintains per-creep combat-target IDs and a one-tick boundary-grace counter. Normal injured-ally support is recomputed from current positions each tick; the activated escort experiment can additionally retain one healer/melee pair for at most 12 ticks. The disabled `src/squads/pair.js` experiment uses stable membership to coordinate one combat leader and healer for at most 24 ticks, with a three-tick failed-progress limit. It does not change healing, attacks, or objectives, and does not implement formations, retreat, or overlays. See [pair eligibility, precedence, and recovery](squad-pair-experiment-2026-10-02.md). Further modules belong under the requested `src/` folders only when the corresponding behavior is introduced.

### Isolated squad-membership bookkeeping

`resetMembership()` creates empty match-local state; `updateMembership(previous, {tick, myCreeps})` returns a new state without Arena or Node.js imports. `runTick()` retains the state and supplies the observed owned creep objects, including their body/health/fatigue and any observed death evidence. Initialization requires tick 1 and exactly 14 distinct, living owned creeps with IDs and positions. A late start, incomplete roster, duplicate ID, or invalid tick remains uninitialized with a reason. A tick reset clears it, while a late module reload cannot reconstruct tick 1. `getMembershipState()` exposes the bookkeeping for inspection; the optional squad-pair planner also consumes the current membership without mutating it.

Initial body types classify pure melee, ranged, healer, scouts with MOVE but no action parts, mixed, and unclassifiable members; TOUGH is passive. Functioning parts are checked separately on updates. Eligible pure healers are sorted by ID; each greedily takes up to three nearest still-unassigned capable melee/ranged creeps by Chebyshev distance, then ID. Groups receive stable IDs; scouts, mixed/unclassifiable creeps, and excess combatants remain explicit unassigned members. This is a deterministic grouping rule, not a formation or a claim of optimal composition.

Membership and initial roles do not reshuffle on injury, fatigue, absence, or part loss. A missing member retains its slot; a returned member resumes it. Only an observed owned creep with `hits <= 0` or `exists === false` is tombstoned—absence alone is not death. Tombstones never reactivate within that match, and no slot is automatically filled. Functioning MOVE plus the original role's action part determines current capability; only capable assigned members are marked participating. Fatigue separately controls immediate mobility, and restored parts reactivate the original slot. Unexpected later IDs are explicitly unassigned. These rules are tested with the recorded 14-member starting composition from replay `6abad54f694bbd0e4ecb70df`. The separate enabled pair screen supports only opening following and lifetime release; sustained squad behavior and strategic benefit remain unverified.

Movement ranks targets by linear distance, not terrain route cost. `moveTo` performs navigation and can fail to make progress because of fatigue, missing MOVE parts, obstacles, or congestion. Mixed-weapon closing, competing injured allies, healer exposure, and approach/fallback switching after the one-tick grace are tradeoffs of this policy. The [combat-positioning validation](combat-positioning-validation.md) records map-linked evidence, local checks, and live-runtime limitations.

The opt-in allocation uses `searchPath` with a bounded operation count to require a complete terrain route and estimate steps for the scout and nearby competitors. A competitor must arrive strictly later than the scout estimate plus five steps; equality rejects the target. Terrain routes omit moving obstacles, fatigue, damage, and future enemy decisions; geometric range is used only as a lower bound when it already proves an enemy is farther away. A capture is not undone when the scout returns: the flag keeps scoring and imposing its army-wide penalty while owned. See the [experiment policy](combat-positioning-validation.md#one-scout-flag-allocation-experiment--2026-09-28).

Local Node.js tests import the pure selection and execution modules. Arena-specific imports stay at the observation and tick-orchestration boundaries (`observe.js` and the optional route search in `loop.js`); `package.json` and Node.js test APIs are for local tooling only. Relative imports remain inside `src/`, because Arena uses the directory containing `main.mjs` as the code root.

## Local replay imports

The local `tools/build-id.js` command generates and verifies `src/debug/build-id.js`. It hashes sorted project-relative paths and exact bytes of runtime `.js`/`.mjs` files under `src/` with NUL separators, excluding the generated file itself and `src/typings/`. The runtime logger emits this ID with pre-action map and game-state entries. The importer records tagged response IDs and a replay association independently of map identity; conflicting tags are rejected, while legacy untagged response provenance stays unknown. See the README for the pre-launch commands and precise hash rule.

`tools/replay-logs.js` is a separate Node.js CLI outside the Arena code directory. It reads cached replay-log responses at startup and polls for changes while the user controls replay playback. Request metadata establishes replay identity; supported version-5 cache framing and gzip payloads yield the original console JSON strings. Arena may join multiple console calls from one tick with a newline; the importer separates and validates each before preserving game-state strings in JSONL. It strictly validates build-tagged membership, action, and CPU evidence alongside the existing allocation and escort diagnostics, retaining original diagnostic lines as typed manifest `otherEntries`, separate from warnings/errors and from game-state JSONL. Per-response `diagnosticCoverage` reports closure, sequence/count gaps, action correlation issues, canonical duplicates, and conflicting record IDs. Typed diagnostics are retained even when their response contains no game state; such evidence-only records do not create JSONL or imply game-state coverage. Missing closure, CPU sample, attempt, or tick remains unknown; legacy, membership-only M2, and M3 responses retain their narrower semantics. Distinct response contents receive separate records, with hash suffixes for JSONL when the replay's canonical filename is occupied. A response's observed tick range does not establish full replay coverage.

The importer extracts the creep-free `map-state` entry, saves its map content with a top-level `checksum` as JSON under `replay_logs/pain_and_gain_map_<UTC-date>.json`, and registers that checksum and map ID in manifest version 2. SHA-256 covers canonical payload JSON plus a newline, excluding only the top-level checksum field; recursive key sorting and array order remain unchanged. A map is validated only when its saved payload passes schema checks and its embedded, registered, and recalculated checksums agree. Identical content reuses a validated registration even across replays. Each replay has its own explicit active map association; there is no global active map. A game-state or typed-diagnostic response arriving before its replay's map is deferred and retried when the map arrives. Every imported record names its map ID, checksum, and file. The JSONL preserves only original game-state console strings. No map is inferred for older unlinked captures.

The explicit `upgrade-map-checksums` command locks the manifest, verifies legacy saved payloads against existing registrations, and atomically embeds missing checksums. It preserves registrations and all manifest bytes, reports failures per map without replacing mismatched values, and is safe to retry. Normal validation requires the embedded field. An orphaned map publication can be reused only after matching the verified incoming payload; a conflicting embedded checksum is rejected. Neither checksum embedding nor validation changes runtime console records.

`replay_logs/manifest.json` has `maps`, `replays`, and `records` collections. File-backed records move from transient import status `pending` to `claim` after JSONL publication; evidence-only records are atomically published directly as `claim`. Task ownership claims are stored separately in `reviews`. Existing `waiting` records migrate to `claim` under the manifest lock without losing checkpoints, map associations, or fingerprints. Records retain source fingerprint, map/build provenance, coverage, other console entries, and per-task review checkpoints. A file-backed record has string `outputPath` and `outputFingerprint` values; an evidence-only record has `null` for both and never creates an empty JSONL. Manifest updates and cleanup share a process lock. A local JSONL file can be explicitly registered only when its replay already has a validated active map association and its game-state flags match that map; JSONL alone cannot prove replay identity. Claims retain records until every claiming task explicitly records examination and completion after saving findings outside the manifest. Only then does the record become `done`; cleanup verifies and deletes a managed JSONL when present, removes the record, and retains map files and registrations. A replay association retains retired fingerprints to prevent unchanged data from reimporting, but not the deleted record's review history. Unregistered reference files are never adopted automatically. Empty version-1 manifests migrate automatically; nonempty version-1 manifests require deliberate migration before using this importer. CLI commands and format limitations are documented in `README.md`.

## Read-only replay analysis

`tools/replay-other.js` supplies the legacy `other` command's native JSONL
serializer and a separately invoked synthetic v3 diagnostic reader. Only the
fixture entrypoint dynamically loads SQLite storage. Its pinned preflight,
bounded output and limitations are documented in the
[M2a record](replay-storage-v3-m2a-2026-10-04.md).

`tools/replay-analysis.js` implements the deterministic M4 analyzer outside the
Arena runtime. Its importable
`analyzeReplay({ root, replayId, fingerprints?, scoreFingerprints?, reportMode? })`
function and guarded CLI read manifest version 2 directly without invoking the
importer's migration, reconciliation, review, or cleanup paths. It validates the
selected record and source metadata, optional JSONL bytes, raw diagnostics,
replay/map linkage, and both canonical map payload and saved-file hashes.

The analyzer merges selected response chunks across file-backed and
evidence-only records. Exact canonical overlaps are deduplicated with all source
references retained; conflicting variants remain visible and make dependent
conclusions unknown. Complete M2, M3, and CPU-covering coverage remain distinct. Membership is
reconstructed only across uninterrupted complete evidence. Recorded attempts
are checked against pre-action positions and functioning parts without rerunning
selectors. Movement displacement and health deltas use only tick-adjacent
snapshots and are reported without engine-effect causality. The stable JSON
report also derives sampling-point CPU headroom without treating it as final
tick CPU or diagnostic overhead, and is written to stdout only. The CLI defaults
to a compact deterministic summary and accepts `--full-detail` for the original
exhaustive contract; the importable API defaults to full mode for compatibility.
Details and report semantics are in
[deterministic replay analysis](replay-analysis.md).

`tools/historical-index.js` is a bounded, local orchestration layer over that
compact analyzer. Its version-1 selection file names exact managed sources and
documented match context; current sources require a task-specific review claim.
It reads the manifest without lifecycle mutations, validates expected runtime
build IDs, and stores ignored per-replay compact reports keyed to relevant
source/map bytes, selected metadata, analyzer/tool code, and configuration.
Rows keep different opponents, maps, builds, partial coverage, and unavailable
retired sources separate. It does not add gameplay logic, runtime logging, or
counterfactual/strategic conclusions. Commands and limitations are in the
[README](../../README.md#bounded-historical-index); the first bounded decision
is recorded [here](historical-evidence-cycle-2026-10-02.md).
